# Фабрика гипотез

Инструмент принимает базу знаний (Excel-отчёты, PDF/DOCX-литературу) и целевой KPI,
на выходе даёт ранжированные проверяемые гипотезы с обоснованием и ссылкой на источник.
Архитектура — **гибрид**: детерминированное ядро рассуждения + LLM только для понимания
неструктурированного текста (с цитатным гейтом) и оценки качества. Логика диагностики
и метрики воспроизводимы; LLM не участвует в выводах, где есть структура, и никогда не
переопределяет уже посчитанный детерминированный результат.

## Логика работы

### Приём (ingest.py)
Загружается что угодно: PDF (pymupdf), DOCX/TXT (xml/plain), XLSX/CSV (openpyxl/csv),
**картинки PNG/JPG/TIFF и сканы** (Yandex Vision OCR). Каждый файл → фрагменты
`Chunk{text, source, locator, kind, meta}`; `meta` несёт метаданные (файл, страница/лист,
дата, `ocr`). Структура на входе не хардкодится.

**OCR (ocr.py, всё через Yandex).** Картинки распознаются Yandex Vision OCR (тот же ключ,
что у LLM; сервис `ocr.api.cloud.yandex.net`, ключу нужна роль `ai.vision.user`). Сканы PDF
(страницы без текстового слоя) растеризуются pymupdf и тоже уходят в OCR. Результат
кэшируется по хэшу изображения (`outputs/ocr_cache.json`) → повторный приём не
перераспознаёт. OCR-текст шумит, поэтому для OCR-чанков цитатный гейт извлечения мягкий
(≥80% слов). Схемы флотации дают подписи узлов (реагенты/операции/классы), связи из них
восстанавливает уже текстовый YandexGPT. Выключается `FACTORY_OCR=0`.

### Разбор запроса (intent.py)
KPI/промпт разбирается ДЕТЕРМИНИРОВАННО (ключевые слова, без LLM — это влияет на
детерминированное ядро, поэтому намеренно без сети): извлекается целевой элемент
(«никель»/«медь» → Ni/Cu) и ограничения («без нового оборудования» → штраф гипотезам,
которые его требуют, без их сокрытия). Раньше был баг: генератор игнорировал KPI и
всегда оптимизировал под Ni — починено.

### Схема формата отчёта (schema.py, schema_bootstrap.py)
Всё формат-специфичное знание (какие подписи-якоря искать, какие элементы и минеральные
формы бывают, порог «тонкого класса») вынесено в `ReportSchema` — конфиг, не хардкод.
Смена формата отчёта = другая схема (JSON-файл), reader.py/rules.py не меняются.
Классы крупности определяются и упорядочиваются ДИНАМИЧЕСКИ по числу в самой подписи
(`class_sort_key`) — без белого списка, работает на любой разбивке по крупности.
Схему для незнакомого формата можно (а) написать вручную, (б) предложить через LLM
ОДНОРАЗОВО (`schema_bootstrap.py` — модель смотрит только на подписи, не на данные;
после сохранения схемы всё дальнейшее чтение снова 100% детерминировано).

### Диспетчер (flex.py)
Каждый файл маршрутизируется по типу:
- **отчёт по хвостам** (xlsx, распознаётся пробным чтением) → детерминированная ветка;
- **прочий текст** (литература, отчёты) → LLM-ветка извлечения;
- эталонные `Гипотезы*.docx` исключаются из знания (это ответы, не источник).

### Ветка A — детерминированная диагностика хвостов
```
reader.py    xlsx → профиль (по схеме): классы крупности × минеральные формы × тонны
             (+ ячейка-провенанс), канонизация классов, #REF!→None, валидация баланса
analysis.py  кривая раскрытия (закрытый/раскрытый минерал по крупности, по целевому
             элементу), «обрыв раскрытия», trade-off, форм-разбивка
rules.py     (доминирующая форма + крупность) → семейство вмешательства [читаемая таблица правил]
metrics.py   impact (доля потерь) · addressability (излечимость) · clarity (ясность механизма) ·
             feasibility · confidence → priority. Всё безразмерно, из данных, без цен.
generator.py карточка ЕСЛИ/ТО/ПОТОМУ ЧТО/ЭКСПЕРИМЕНТ + заземление до ячейки + источники
             метода; помечает нарушенные ограничения промпта, не скрывая гипотезу
```
Без LLM, ~0.03 c, тот же файл + та же схема → тот же результат.

### Ветка B — извлечение из текста → граф → открытие
```
extract.py   LLM читает фрагмент, возвращает связи (subject —тип→ object) с ДОСЛОВНОЙ
             цитатой + пометкой is_action (промышленное действие или абстрактный факт).
             Тип связи — из закрытого словаря {повышает/снижает/не_влияет/связан} →
             знак детерминирован. Цитатный гейт: цитата обязана быть подстрокой
             фрагмента, иначе связь отбрасывается. Результат кэшируется →
             downstream воспроизводим. Отбор фрагментов — по релевантности KPI.
kgraph.py    связи → канонический граф (networkx), нормализация сущностей, провенанс+метаданные
discover.py  разрывы Свонсона (A→B, B→C, нет A→C) + прямые рычаги (связь к KPI-сущности);
             промышленные действия (is_action) получают бонус к рангу и формулируются как
             рекомендация «внедрить X»; абстрактные факты — честно как «исследовать
             применимость», не выдаются за готовое решение. Детерминированно поверх кэша.
```
LLM только извлекает; вывод (граф, разрывы, ранг) детерминирован после кэша. Единственное
место, реально зовущее LLM на извлечение — `extract_relations`, вызывается из `flex.py`.

### Отчёт и оценка
- `report.py`/`glossary.py` → самодостаточный HTML: граф (SVG), кривая раскрытия, форм-таблица,
  карточки (источники, эксперимент, заземление), глоссарий метрик. `outputs/<фабрика>_гипотезы.html`.
- `evaluate.py` → сверка ОДНОЙ фабрики с ОДНИМ эталоном по семействам вмешательства.
- `benchmark.py` → сводный евал: ветка А по ВСЕМ фабрикам (golden-coverage) + судья по
  ВСЕМ гипотезам системы (обе ветки) одним прогоном.
- `judge.py` → **LLM-as-judge** — качественная метрика ВСЕХ гипотез (хвосты + литература) по
  единой рубрике (обоснованность · правдоподобность · релевантность KPI · неочевидность ·
  проверяемость). Оценивает готовое — ничего не переранжирует. Ветку Б **не извлекает сама**,
  только читает кэш, наполненный `flex.py` — так исключён рассинхрон путей/лимитов между
  командами. Вердикты кэшируются по отпечатку → воспроизводимы.
- `docs/build_guide.py` → PDF-гайд разработчика (reportlab).

## Установка

```bash
uv sync
cp .env.example .env    # если файла нет — создать вручную, см. ниже
```

`.env` (в корне репозитория, вне git) для LLM-веток:
```
YANDEX_API_KEY=...
YANDEX_FOLDER_ID=...
```
Без ключа детерминированное ядро (ветка А) работает полностью; всё, что трогает
литературу/схему-бутстрап/судью/полировку текста, требует ключ и мягко откажется без него.

## Все команды CLI

### Не требуют ключа Yandex (100% детерминированно)

**Одна фабрика → консоль + HTML с графом.** Основной путь для одного отчёта.
```bash
uv run python -m factory "materials/fabrics/ТОФ/Хвосты ТОФ_2.xlsx" \
  --kpi "снизить потери меди с хвостами" \
  [--schema outputs/schemas/имя.json] \
  [--polish] [--out путь.html]
```
- `--kpi` — **обязателен**. Без него команда завершится ошибкой с понятным сообщением,
  а не молча подставит какую-то цель за вас — какой элемент/направление оптимизировать,
  решает пользователь, не система. Если в тексте KPI не упомянут элемент явно
  («никель»/«медь»/Ni/Cu) — используется Ni, но об этом ПЕЧАТАЕТСЯ явное предупреждение.
- `--schema` — своя схема формата (см. `schema_bootstrap.py` ниже); по умолчанию известный формат.
- `--polish` — LLM-полировка текста карточек (требует ключ; без ключа тихо игнорируется).
- `--out` — куда сохранить HTML; по умолчанию `outputs/<фабрика>_гипотезы.html`.

Файл отчёта тоже проверяется на существование заранее — понятная ошибка, а не
крипто-трейсбек, если путь неверный.

**Сверка ОДНОЙ фабрики с ОДНИМ эталоном** (по семействам вмешательства). Это
регрессионный тест диагностики против эталона инженеров, а не ответ на реальный
вопрос — KPI необязателен (виден явный тестовый KPI в `evaluate.py`, можно переопределить
третьим аргументом):
```bash
uv run python -m factory.evaluate "materials/fabrics/ТОФ/Хвосты ТОФ_2.xlsx" \
                                   "materials/fabrics/ТОФ/Гипотезы ТОФ.docx" \
                                   ["свой KPI"]
```

**Golden-бенчмарк по ВСЕМ фабрикам** (без судьи — только ветка А; по той же причине
`--kpi` тут не нужен — используется явный тестовый KPI, см. выше):
```bash
uv run python -m factory.benchmark --no-judge [materials/fabrics]
```

### Требуют ключ Yandex (LLM-ветка)

**1. Гибкий приём — сначала это.** Диагностирует хвосты (детерминированно) И извлекает
знание из литературы в кэш графа. **Это единственная команда, которая реально зовёт LLM
на извлечение** — остальные LLM-команды ниже только читают то, что она наполнила.
```bash
uv run python -m factory.flex materials --kpi "снизить потери никеля с хвостами" \
  [--max-chunks 24] [--cache outputs/kb_cache.json] [--no-cache]
```
Пишет HTML по каждой найденной фабрике в `outputs/` и кэш графа литературы
(`--cache`, по умолчанию `outputs/kb_cache.json`) — на нём работают команды ниже.

**2. Судья — после flex, читает кэш.** Оценивает ВСЕ гипотезы системы (хвосты + то,
что нашёл flex в литературе) по единой рубрике 1..5. `--kpi` **обязателен** — судья
должен явно знать, релевантность чему оценивать.
```bash
uv run python -m factory.judge --kpi "снизить потери никеля с хвостами" \
  [--fabrics materials/fabrics] [--cache outputs/kb_cache.json] \
  [--no-tailings] [--no-literature] [--judge-cache outputs/judge_cache.json] [--no-cache]
```

**3. Сводный евал — то же самое одним прогоном** (golden-coverage ветки А + судья по обеим).
`--kpi` обязателен, ЕСЛИ судья реально запускается (т.е. без `--no-judge`) — при
`--no-judge` не нужен (ветка А использует явный тестовый KPI, как в `evaluate.py`):
```bash
uv run python -m factory.benchmark [materials/fabrics] \
  --kpi "..." [--cache outputs/kb_cache.json]
# либо без судьи, kpi не нужен:
uv run python -m factory.benchmark --no-judge [materials/fabrics]
```

**Схема для незнакомого формата отчёта** (не обязательно после flex — отдельная задача):
```bash
uv run python -m factory.schema_bootstrap "путь/к/незнакомому_отчёту.xlsx" \
  [--out outputs/schemas/имя.json]
```
LLM смотрит только на подписи (не на данные), предлагает схему один раз, сразу
прогоняет пробный парсинг и печатает, сходится ли баланс. Схему проверить/поправить
вручную и использовать через `--schema` в `factory`/`factory.flex`.

### Утилиты

**PDF-гайд разработчика** (reportlab, требует системные шрифты DejaVu, ключ не нужен):
```bash
uv run python -m factory.docs.build_guide   # → DEVELOPER_GUIDE.pdf в корне
```

## Рекомендованный порядок на новых данных

0. Сформулировать реальный KPI (цель) — без него ничего не запустится, это осознанно.
1. `factory <report.xlsx> --kpi "..."` — быстрая проверка, что отчёт вообще парсится
   (если нет — смотри `warnings` в выводе, возможно нужна своя схема).
2. Если формат незнакомый и есть предупреждения парсинга — `factory.schema_bootstrap`,
   проверить/поправить сохранённую схему, повторить (1) с `--schema`.
3. `factory.flex materials --kpi "..."` — полный прогон: диагностика всех фабрик +
   извлечение из всей доступной литературы в кэш. Если путь пуст/файлов не нашлось —
   команда явно об этом скажет, а не проработает молча вхолостую.
4. `factory.benchmark --kpi "..."` — сразу обе метрики (golden-coverage + судья) одним
   прогоном (или `--no-judge`, если нужна только golden-coverage без ключа/KPI).
5. По необходимости точечно: `factory.evaluate` (одна пара, KPI необязателен —
   регрессионный тест) или `factory.judge` (только судья, гибче по флагам, KPI обязателен).

## Настройка (env / `.env`, см. `factory/config.py`)

KPI НЕ настраивается через env/дефолт — только явным `--kpi` в каждой команде (см.
выше). Остальное: `FACTORY_OUTPUTS`, `YANDEX_MODEL`, `YANDEX_BASE_URL`,
`FACTORY_LLM_WORKERS` (параллельность извлечения, по умолчанию 2 — больше → чаще 429),
`FACTORY_LLM_RETRIES`, `FACTORY_FRAGMENT_RETRIES` (повтор упавших фрагментов
последовательно, не толпой), `FACTORY_MAX_CHUNK_CHARS`, `FACTORY_MIN_PROSE_CHARS`,
`JUDGE_MODEL` (модель судьи; в идеале ≠ модели-экстрактору). Кэш графа несёт отпечаток
входа (KPI+фрагменты) и сам инвалидируется при их смене — судья/бенчмарк это НЕ
переизвлекают сами, только `flex.py`.

## Результаты (реальные данные)
- Детерминированная диагностика: 4 фабрики, гипотезы ранжированы по impact, каждое число —
  до ячейки. Golden-сверка: **23/27 = 85%** (ТОФ/КГМК 100%, НОФ_вкр 83%, НОФ_мед 62%).
- Литературная ветка: из справочника по флотации извлекаются связи с цитатой до страницы,
  промышленные действия (is_action) формулируются как рекомендации к внедрению.

## Соответствие критериям ТЗ

| Критерий | Статус | Как закрыт |
|---|---|---|
| Вход: KPI + база знаний | ✅ | KPI-строка + папка любых файлов |
| Приём/парсинг литературы (PDF/статьи/отчёты) | ✅ | ingest.py (pymupdf/docx) |
| Импорт структурных данных | ✅ | reader.py по схеме (xlsx-отчёты), csv/xlsx как таблицы |
| Метаданные (источник/дата/страница) | ⚠️ | file/page/sheet/date; автор — нет |
| Извлечение сущностей и связей | ✅ | extract.py (LLM + цитатный гейт + is_action) |
| Пробелы/паттерны | ✅ | разрывы Свонсона + прямые рычаги (discover.py) |
| Аналогии / контрфактуал / предсказание | ⚠️ | разрывы ≈ аналогии; контрфактуал/ML — нет |
| Ранжирование (новизна/реализуемость/эффект/риск) | ✅ | детерминированные метрики + action-бонус |
| Обоснование + ссылки на источник + эксперимент | ✅ | заземление до ячейки/цитаты, `experiment`, `sources` в карточке |
| Визуализация связей (граф) | ✅ | SVG-граф + кривая раскрытия в HTML |
| Оценка неопределённости | ⚠️ | confidence + валидация парса; противоречия не разрешаются |
| Прозрачность/интерпретируемость | ✅ | правила и метрики читаемы, «цитата» = координата/подстрока |
| Гибкость входных данных | ✅ | гибридный приём + схема формата (не хардкод) |
| Надёжность к шуму | ⚠️ | #REF!→None, цитатный гейт, валидация баланса; без разрешения противоречий |
| Производительность (минуты) | ✅ | ядро ~0.03 c; извлечение — минуты, кэшируется |
| Масштабируемость на новые области | ✅/⚠️ | формат хвостов — схема (не хардкод); домен химии (не Cu-Ni) — нужна новая схема+правила |
| Экспорт PDF/DOCX/CSV/JSON, Jira | ⚠️ | HTML-отчёт + PDF-гайд; бизнес-PDF/DOCX и задачи — нет |
| Мультиязычность RU/EN/CN | ⚠️ | RU; EN — через LLM; CN не проверено |
| Безопасность (локально) | ⚠️ | ядро локально без ключа; LLM-ветка — облако Yandex |
| Экспертная настройка весов | ⚠️ | веса/цены/правила редактируемы в коде, не в UI |
| Мировая практика / подтверждено внедрением | ⚠️ | явный `world_practice` placeholder в карточке — ждёт модуль веб-поиска |
| Дорожная карта эксперимента | ❌ | не реализовано (есть только протокол одного эксперимента) |
| Обучение на фидбэке | ❌ | не реализовано |

## Структура
```
factory/
  schema.py schema_bootstrap.py intent.py               ← конфиг формата + разбор KPI (без LLM в ядре)
  ingest.py extract.py kgraph.py discover.py flex.py     ← гибкая ветка (текст → граф → открытие)
  reader.py analysis.py rules.py metrics.py generator.py pipeline.py  ← детерминированная ветка (хвосты)
  config.py llm.py report.py glossary.py evaluate.py benchmark.py judge.py docs/build_guide.py
materials/   fabrics/<Ф>/ (Хвосты+Гипотезы) · reference/ (books/schemes/regulations)   [вне git]
outputs/     HTML-отчёты, kb_cache.json, judge_cache.json, schemas/                    [вне git]
```
